# Asynchronous playback intent

`SessionPlayback` is an observable main-actor interface for one finite session. Initialization stores the bank URL and immutable planning inputs without reading the bank, creating a worker, or activating playback. Explicit `play()` lazily constructs the real preparer, preparation worker, and `SessionAudioEngine` on one default-QoS serial control queue. Every engine access and final release stays there; the main actor never waits for preparation or joins a worker.

Play, Pause, terminal Stop, refresh, and explicit preparation retry update one locked command record. There is one scheduled control drain and one pending main-actor delivery; rapid commands replace intent instead of appending a history of closures. Snapshots carry a revision so an obsolete completion cannot replace newer intent. The callback and renderer are unchanged and never enter this mailbox.

Pause or Stop immediately cancels an in-flight startup token. If a factory still returns a completed engine, the control queue stops and releases that obsolete result before admitting a replacement. Pause after readiness retains the existing graph and musical position. A duplicate Play during blocked startup does not turn a failure into an automatic retry; explicit Play after failure can start a fresh attempt. Pause followed by Play during canceled startup admits at most one fresh attempt after old cleanup.

An already-admitted engine start cannot be preempted synchronously by a later command. The queue reconciles newer intent after it returns, suppressing stale state publication. Genuine failures remain visible; only cancellation from an actually canceled attempt is treated as expected cancellation. Terminal Stop is acknowledged after engine shutdown, preparation join, owner release, and the operation's autorelease-pool drain. Releasing the main-actor facade schedules the same cleanup without blocking its caller. A stopped coordinator cannot be reused.

State, errors, source status, preparation status, and generated canonical position are acknowledged snapshots, not an audible playhead or a continuous monitor. `refresh()` samples the current graph without starting it. In particular, refreshing or retrying after an external graph pause cannot resume output; only a new explicit Play authorizes that. `retryPreparation()` is coalesced and never creates a session or resumes output. When Play and retry arrive together, retry follows the requested resume so it is not lost to the worker's suspended state. Genuine successor errors survive pause and remain observable after stop.

There is no production polling timer, automatic EOF stop, or automatic error retry. The host must request snapshots as appropriate and handle source/preparation failures, sustained waiting, and conversion drain. Audio-session policy, interruption/route notifications, background/remote controls, restoration, and the app's Play/Pause interface remain separate work. Device-mode engine start can implicitly activate the audio session, so the host must configure the intended policy before requesting Play.

Six focused tests use real offline engines and deterministic startup gates. They cover mixed command bursts ending in Pause, late successful startup disposal, duplicate Play failure latching, a fresh Pause/Play generation, terminal Stop and facade destruction during startup, an actual start that renders 113 frames before failing, exact four-song output through pause/resume and explicit successor retry, and read-only refresh after an external graph pause. Main-actor tests never wait on semaphores or join threads; the gates hold only control work. Existing worker tests retain separate coverage of cancellation during real analysis. The iOS integration test constructs and controls the same graph through this coordinator.

During gated startup, control actions and gate release run together on the main queue; assertions remain in the test task. This keeps the intended race deterministic when the full concurrent Debug suite is busy, with unchanged 30-second safety bounds.

Local validation with the pinned Xcode 26.6 toolchain passed all 112 audio tests in 34 suites in both Debug and Release. A focused Thread Sanitizer run passed 30 lifecycle/concurrency tests in seven suites using Release optimization and a serialized test harness; the actual control, worker, and rendering roles remain concurrent. The iOS simulator passed nine integration tests and the launch UI test, and the unsigned iOS Release build succeeded. Formatting, repository checks, and all 13 CodeQL coverage-guard tests passed.

All 193 deterministic exports (161 PCM files and 32 scalar JSON files) are byte-identical to PR #44. The existing engine, worker, callback, renderer, planner, sound bank, fixtures, and reference tools are unchanged. Original-reference comparisons were not rerun locally; hosted audio, size, build, and security checks remain separate required results. Offline/simulator checks do not establish physical-device startup latency, background reliability, or energy use.
