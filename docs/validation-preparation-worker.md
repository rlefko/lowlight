# Managed session preparation

`SessionPreparationWorker` owns one dedicated thread that constructs a concurrent `PreparedSession` and automatically prepares each successor. Its throwing initializer waits for both initial songs, so construction belongs off the main and audio threads. The optional constructor token cancels startup; use `requestStop()` afterward. Call `makeRenderEndpoint()` once on the control thread, then keep that endpoint alive for one render consumer.

The worker uses a 100 ms timed wait between idle checks of the existing atomic handoff. The callback never signals a condition, acquires a worker lock, or performs preparation. This polling interval is a scheduling choice, not a preparation deadline; a late successor still uses the existing pause at its missing onset. Native rendering, planning, musical timing, sample limits, and the render endpoint are unchanged.

One failed successor attempt is latched as `waitingForRetry` with `lastError`. `retry()` coalesces one explicit request and uses a fresh cancellation token for the same pending schedule. It does not spin on repeated failures. `requestStop()` is terminal and cooperatively cancels the active attempt. Initial publication and successor token installation share the control lock with stop. Individual decoding and native setup operations remain noninterruptible, and an attempt that passes its final cancellation check may still succeed.

`join()` waits only for preparation; simultaneous callers share one thread join. Finite EOF or a render fault also stops preparation. Neither worker exit nor the atomic EOF snapshot proves the render callback has returned. The worker therefore retains the session after its thread exits, and an issued endpoint can retain it after the worker is released. Stop and join the consumer separately, then release its endpoint and the worker off the callback. Deinitialization requests stop and joins, so final release can block. No pause, restart, device output, or audio-session integration is added.
