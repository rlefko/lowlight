# Testing and contributing

Run `./scripts/setup` once after cloning. It verifies the pinned Xcode/Swift and bundled clang-format versions, downloads SwiftLint with checksum verification, and installs the tracked Git hooks. Development setup needs internet access; the app does not. Use `./scripts/quality fix` for explicit Swift and native formatting and `./scripts/quality` to check without changing files. The clang-format tool comes from the already required Xcode installation; there is no additional download.

Native formatting uses `.clang-format`: four-space indentation, a 100-column limit, and no include or using-declaration sorting or comment reflow. Include order matters because the DSP numeric-environment header must remain first. All tracked C, C++, Objective-C, and header files are checked, including native tests. `.clang-format-ignore` explicitly preserves `NumpyRandom.cpp` and `NumpyZiggurat.h`, which contain adapted upstream implementation, unchanged tables, and embedded license notices; project-owned `NumpyRandom.h` remains included. The existing upstream provenance and license checks still apply.

The pre-commit hook invokes `scripts/quality staged` against a temporary snapshot of the Git index, including staged formatting configuration. It checks complete staged files without changing the index or working files. A staged native style or exclusion change, including a nested configuration, checks every native file in the index. Formatting inputs exclude unstaged edits and untracked files; the hook and toolchain prerequisite scripts still execute from the working checkout. Explicit `fix` updates tracked working files only and never stages them; review and stage the intended changes yourself. Run the real-tool hook regressions with `python3 -B -m unittest discover -s tests -p 'test_quality.py'` after setup.

Pre-commit checks whitespace and staged Swift files from an index snapshot, so partial staging is preserved. Nothing is automatically staged or rewritten. The commit-message hook requires an emoji and one concise sentence fragment without final punctuation.

Use one focused behavior change per PR. Titles start with an emoji and use short Title Case; branches use `rlefko/` plus the title in kebab case without its emoji. Keep handwritten code near 300–500 changed lines, explaining coherent exceptions. Include relevant validation and material limitations. The owner reviews the concrete result before merging; no automatic merges or direct feature pushes to the default branch.

## Checks

`./scripts/test-dsp` runs the C++ kernel tests optimized and with AddressSanitizer/UndefinedBehaviorSanitizer, including allocation and voice-limit audits. `./scripts/test-audio` (or `release`) checks native instrument preparation, complete voice output, and malformed input boundaries. CI transfers the macOS Release samples to the Linux Audio Regression job for comparison against the original Python functions and retains dry-note A/B evidence; see [tonal preparation](validation-tonal.md) and [voice validation](validation-voices.md), [bass validation](validation-bass.md), [percussion validation](validation-percussion.md), [rhythm bus validation](validation-rhythm.md), [harmonic glue validation](validation-glue.md), [stereo room validation](validation-room.md), [peak protection validation](validation-peak.md), [song fade validation](validation-fades.md), [quiet-air validation](validation-air.md), and [song-mix validation](validation-mix.md).

The independent scheduled-song tests use Swift Testing’s default concurrent scheduling. See [the scheduling validation](validation-ci-audio.md) for the local screening, CPU/memory tradeoffs, and unchanged coverage requirements.

`./scripts/test-planner` runs Swift Testing on the native planning package without a simulator or audio hardware; add `release` to verify the same vectors with production optimization. `./scripts/build test` runs native bank/planning integration checks and the launch/About/dismiss/relaunch UI smoke test. `./scripts/build release` builds the unsigned device app used by size reporting. Use XCTest/XCUITest for UI and appropriate performance coverage.

Tests create a temporary device using the runtime and device type pinned in [toolchain.env](../config/toolchain.env), wait for it to boot, and delete only that device afterward. Install the pinned runtime in Xcode Settings > Components for local development. CI initializes Xcode and downloads that exact runtime only if it is missing; it never substitutes another OS version. Set `SIMULATOR_DESTINATION` to an explicit Xcode destination to use an existing device instead.

CI runs Quality, Build and Tests, Native Tests, Debug Audio Tests, Audio Regression, Size Budget, CodeQL (Swift/C++/Python), and an always-running CI Gate. Build and Tests runs iOS integration/UI tests independently of the package checks. Native Tests runs planning in Debug and Release, the complete native DSP suite, and Release audio tests with candidate exports. Debug Audio Tests runs the complete unoptimized audio suite on its own runner. Audio Regression waits only for Native Tests to produce its candidate artifact. CI Gate requires the exact seven upstream job IDs and successful results for all of them, including both new test jobs; skipped, cancelled, missing, or failed jobs cannot pass.

Audio Regression verifies the bank, frozen reference, derived grammar, and independent event oracles, then reproduces the short sound fixtures using pinned developer dependencies. Native Swift Testing checks every bundled note's decoder output and resource membership. CodeQL analyzes Swift and C++ in separate Intel jobs, each running the same clean app build; Python tools run in a separate Linux job. Long session soaks, physical-device energy trials, and signed exports stay outside commit hooks and ordinary PR checks.

The [first PR48 run](https://github.com/rlefko/lowlight/actions/runs/42084986343/job/127447547998) exceeded the former combined job's 30-minute limit during cleanup, after all tests and Xcode's `TEST SUCCEEDED` had completed. Debug audio occupied 16m30s, Release audio 2m11s, and simulator startup/build/tests about 8m36s, in addition to planner/native checks and artifact work. The independent jobs remove that serial accumulation without filtering tests, changing compiler flags, or increasing the Debug/simulator timeouts. Actual wall time still depends on hosted runner speed and capacity. `tests/test_ci_workflow.py` checks command coverage and artifact wiring and executes the real gate against success, failure, cancellation, skipped, missing, and unexpected results.

Both native CodeQL jobs use standard Intel runners while compiling fresh arm64 app/package targets with compilation caches disabled. Swift and C++ extraction/analysis run in parallel; each job verifies its own source inventory. After analysis, `scripts/verify-codeql-coverage.py` checks the decoded inventories against tracked app/package Swift sources, package manifests, and C/C++ package sources/headers. The retained `swift-extraction-inventory` and `cpp-extraction-inventory` artifacts support coverage review. Run its failure-path tests with `python3 -B -m unittest discover -s tests -p test_codeql_coverage.py`. See [CI performance evidence](performance.md#ci-performance-follow-up) for timing and validation limits.

CodeQL setup uses the pinned bundle's Zstandard archive through the pinned action's supported extraction path. The hosted images provide compatible tar and zstd tools. Tool-cache hits may skip download/extraction; compare cache misses and those setup phases separately from the fresh app trace. See [archive measurements](performance.md#codeql-archive-setup) for content verification and timing limits.

Manual workflow runs require a `size_base` commit/ref. Enable `codeql_debug` only when tracer logs and database bundles are needed (`codeql-debug-swift` and `codeql-debug-cpp`); ordinary runs retain the small extraction inventory and build timings. PRs compare against their actual merge base; main-branch runs compare against the previous head. A missing project counts as a first size baseline only when the base tree is empty.

The active [main-branch ruleset](https://github.com/rlefko/lowlight/rules/26254576) requires PRs, resolved review conversations, an up-to-date CI Gate from GitHub Actions, and CodeQL findings protection. Force pushes and deletion are blocked, with no bypass actors. CodeQL errors/warnings and medium-or-higher security findings block merging. Read the active branch rules back through GitHub's API when changing protection; workflow YAML alone is insufficient. Owner-authored PRs use mandatory CI and an explicit manual review/merge handoff because GitHub cannot accept self-approval.
