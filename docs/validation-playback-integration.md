# Continuous listening and app transport

Lowlight now owns one ongoing playback session from the app's lifetime. Launch reads bounded, versioned musical intent off the main thread and remains silent until Play. Play/Pause and Next are accessible native controls; About retains the existing code and sound-library notices. Entering the background captures the current place without pausing playback. The built app declares the `audio` background mode. MediaPlayer registers Play, Pause, Toggle, and Next, with semantic metadata and no invented duration or seek position.

All commands enter the coordinator's existing bounded mailbox synchronously, including arbitrary-thread remote handlers. Toggle flips the latest requested intent. Explicit Play retries failed startup or recovery; the app's failed-state primary action sends Play directly. Reset revokes previously admitted playback intent before returning from its notification. Captured late remote handlers reject input after their adapter is invalidated. Cleanup removes only owned target tokens, and an older owner's delayed metadata cleanup cannot clear a newer owner's metadata.

## Ongoing transport and musical Next

The existing two-rack renderer and global peak protector support an explicit ongoing mode. Session clocks and placement are 64-bit integers bounded by the planner's exact frame domain; a session no longer uses the old 32-bit finite extent as an artificial duration. Child render lengths and callback capacities remain bounded 32-bit values. Existing finite entry points retain their exit fades, EOF behavior, and converter-drain limits.

Next retains one selected-song target. The worker offers the earliest eligible eight-bar boundary before the original outro, with enough physical-input lead for the damping window. It translates the already compatible four-bar pivot and its successor by an integer frame offset. Both sides keep their shared tempo ramp, linear tonal fades, and midpoint bass/drum ownership transfer. An already occurring natural handoff satisfies the target. A request made during overlap waits for the old tail's retirement and a prepared successor; Next while paused grants no playback permission.

The worker builds an immutable replacement event table, preserving the indices used by live voices and rejecting edits that exceed the combined 64-voice limit. Incompatible live harmonic notes receive a multiplicative 110 ms cosine-squared release; an already-releasing voice cannot become louder. Compatible notes, rhythm tails, filters, room state, measured gain, and both peak stages survive the edit. This live-edit policy is new behavior, not a claim that the original prototype implemented live Next.

The callback adopts only pointers and bounded state. It performs no score scan, allocation, reclamation, file work, or locking. The offered owners and table remain alive through acknowledgment and native destruction. Next publication is separate from rack retirement. A proposal that misses its deadline leaves the original timeline intact and can retry a later feasible phrase. If none remains, the natural handoff fulfills the request. Successor preparation errors expose an explicit retry while retaining the current graph; terminal render faults dispose the graph and require a new Play.

## Restoration and persistence

The selected song changes at the shared rhythm handoff, independently of the planning cursor ahead of playback. Worker-owned records retain the checkpoint belonging to each admitted rack. Captures map the transport cursor back into that selected song's canonical musical clock, including any earlier Next translation. The existing worker cadence emits semantic changes; there is no new app polling timer or per-callback task. Pause and background captures can wake suspended preparation without resuming audio.

A saved intent contains the versioned planning checkpoint and its validated canonical position. It contains no PCM, device objects, paths, autoplay flag, or queued Next command. An accepted transition that has not reached its musical boundary is not restored as a future action. Restoration prepares the selected song and one successor, renders at most that song's prefix off the callback, and fades in from the saved position. It does not reproduce a predecessor's overlapping tail, the old session protector history, or the audible device playhead sample-for-sample. Engine configuration changes retain the live renderer; media-server resets instead rebuild from the latest captured intent after explicit Play.

Persistence uses one serial atomic file replacement and one coalesced pending intent. Selection changes, acknowledged pause/failure/stop, and background entry save the latest available place. Missing files are ordinary first launch; corrupt or unsupported files remain intact until the user chooses a fresh session. Failed writes preserve the latest intent for Retry and do not interrupt music. An older load cannot replace a newer fresh-session choice. Atomic replacement is not a power-loss durability guarantee, and abrupt termination can lose progress since the last completed capture/save.

## Validation boundaries

The new native transport and Next suites passed optimized, Address/Undefined Behavior Sanitizer, and Thread Sanitizer modes. They cover clocks beyond 2³², finite/ongoing bounds, allocation-free callback work, caller floating-point state, partition identity, immutable publication/acknowledgment, retirement, and real-chain edited-score comparison. [The Next tests](../tests/dsp/SongNextTests.cpp) include independently frozen sustaining/already-releasing envelope values and half-open lifetime admission checks. Simulator tests exercise the real engine and native DSP with offline rendering; they do not establish hardware deadlines, lock-screen delivery, Bluetooth converter quality, or battery equivalence.

A local Release soak generated exactly 230,400,000 frames (two hours at 32 kHz) through the public ongoing worker and render endpoint: 87 observed selections, 21 Next requests, and 17 observed early integer-placement advances, with finite non-silent PCM, no render/preparation errors, and clean shutdown. Peak sample magnitude was 0.7763191 and process maximum RSS was 90.31 MiB. The accelerated render completed in 147.73 seconds while other validation ran; this is not a controlled throughput or energy benchmark. Zero/short pulls represented uncounted preparation waits, not inserted PCM or proof of real-time device readiness. Live rack counters were not observed through this public API; their limits are independently tested admission invariants.

All 140 audio tests in 41 suites passed in Debug and Release; all 193 preserved exports (161 PCM and 32 scalar files) remained byte-identical to PR47, and all 14 original-reference comparisons passed unchanged. The 58 focused playback/worker tests in 14 suites passed under Thread Sanitizer without sanitizer warnings. Both planner configurations, the complete native DSP script, repository/asset checks, formatting/lint, and the 23 formatting/coverage-guard tests passed.

The integrated simulator suite passed 27 tests in six suites, plus the Play/Pause, About, and silent-relaunch UI flow. Tests cover actual MediaPlayer metadata/command enablement, arbitrary-thread command submission, late registration cleanup, fresh-start/load races, serialized/coalesced saves, and persistence failure recovery. The Debug and Release built plists both contain only `audio` in `UIBackgroundModes` and no microphone usage declaration.

The unsigned arm64 Release app measured 10,856,448 bytes (1,852,952 executable, 9,003,496 resources), 452,252 bytes above the equivalent PR47 build and within the existing budget. This is an unsigned build proxy, not a signed/thinned download estimate.

Physical-device acceptance remains required: use a signed Release build, record device/iOS/route/commit, verify offline first launch, lock-screen and other-app playback through multiple handoffs, remote Play/Pause/Next, interruption resume permission, user Pause during interruption, wired/Bluetooth disconnect/reconnect and sample-rate changes, actual media-services reset, silent relaunch, and saved-position recovery. Repeat under long listening and inspect glitches, memory, thermal behavior, and energy. These are release gates, not claimed simulator results.
