# Playback interruptions and output disconnection

`SessionPlayback` now observes iOS audio-session interruptions and output disconnection through the same bounded command mailbox used by Play, Pause, and Stop. Registration is lazy, before the first preparation attempt; observers remain through pause and failure and are removed on terminal cleanup or facade destruction. Notification callbacks synchronously invalidate obsolete startup on their posting thread. They perform no engine work, wait for no worker, and enqueue no per-event task.

An interruption begin cancels startup and requests graph pause, preparation suspension, and session deactivation on the existing serial control queue. The latest user intent survives. A matching end resumes only when its options include `shouldResume` and Play remains the desired action. User Pause, Stop, and output disconnection suppress that automatic recovery. Duplicate begin and unmatched end notifications do not restart output. Even when begin and end arrive before the queue drains, it quiesces the old output before reactivation. An existing startup failure remains latched until a new explicit Play.

Explicit Play clears interruption gating and attempts activation again. This provides recovery when the system never delivers an end event; activation can still fail if the session is unavailable. A later end for the superseded interruption is ignored. `isInterrupted` is an acknowledged coordinator flag, not an independent measurement of system session activity. The iOS 18-compatible notification contract follows Apple's [interruption guidance](https://developer.apple.com/documentation/avfaudio/handling-audio-interruptions); the newer lifecycle APIs require an OS beyond the project's deployment target and pinned SDK.

An `oldDeviceUnavailable` route notification revokes Play intent and pauses the retained graph. Connecting an output does not autoplay; the user must issue Play again. An interruption whose reason is `routeDisconnected` applies the same policy even if the separate route notification is absent. Duplicate disconnection events do not repeatedly retry failed cleanup. The adapter ignores unrelated route reasons, malformed interruption types, and notifications for another session. See Apple's [route-change guidance](https://developer.apple.com/documentation/avfaudio/responding-to-audio-route-changes).

The existing control queue still owns every graph operation, system session call, and final release. One scheduled drain and one pending main-actor snapshot serve notification bursts and user controls together. Snapshot revisions are checked against the mailbox at delivery, including revisions created by system events. Notification removal and snapshot receivers run outside mailbox locks. An already-admitted start or activation cannot be preempted synchronously; newer intent is reconciled after it returns, before its acknowledgment. This is not a zero-frame guarantee during physical output removal.

Five package test groups retain real offline engines and workers. They verify bitwise continuity of 50,003 generated stereo frames across matched and coalesced interruptions, intent and permission precedence, immediate off-main cancellation during gated startup, failed-startup latching, lazy registration, terminal/destruction cleanup, and ignored late callbacks. iOS tests exercise raw notification decoding and observer removal on a private notification center, plus the actual session configuration/activation adapter with a real offline graph through interruption and route-loss recovery.

Graph rebuilding after sample-rate/configuration changes, media-services reset recovery, app controls, background mode, remote commands, and physical-device interruption/headphone tests remain separate work. The canonical renderer, preparation worker, engine owner, sound bank, planner, and audio callback are unchanged.

Local validation with the pinned Xcode 26.6 toolchain passed all 122 audio tests in 36 suites in both Debug and Release. The focused Thread Sanitizer run passed 40 tests in nine suites with no sanitizer warnings, using Release optimization and a serialized test harness while the actual control, preparation, and rendering roles remain concurrent. Ten iOS integration tests, the launch UI test, and the unsigned iOS Release build passed, along with formatting, repository checks, and all 13 CodeQL coverage-guard tests.

All 193 deterministic exports (161 PCM and 32 scalar JSON files) are byte-identical to PR #46. Original-reference comparisons were not rerun locally; hosted regression, size, build, and security checks remain separate required results. Simulator/offline evidence does not establish physical-device latency, background reliability, or energy use.
