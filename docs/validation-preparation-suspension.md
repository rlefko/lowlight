# Reversible preparation suspension

`SessionPreparationWorker.suspend()` requests a cooperative pause of background preparation. It returns true for a new request and false for a repeated request or a stopped worker. The `.suspended` status acknowledges that the active attempt has returned and released any unfinished candidate. The dedicated worker then waits on its condition without timed polling. EOF, a render fault, or terminal stop can win first and report `.stopped` instead. This is a preparation acknowledgment, not a render-consumer acknowledgment.

`resume()` clears the request and wakes the worker. A canceled attempt must finish before a fresh token can prepare the same pending schedule. The current racks, render endpoint, canonical position, effect history, and planning state stay alive. A quick suspend/resume can bypass the acknowledged suspended state; cancellation from that attempt still does not become a preparation error. A candidate past its final cancellation check may be admitted before suspension is acknowledged.

Genuine failures remain in `lastError`, including failures racing suspension. Resume does not clear them: an explicit `retry()` is still required. Retry is rejected while suspension is requested; a retry already accepted before suspension remains pending. `requestStop()` remains terminal, wakes suspension, and cooperatively cancels preparation. `join()` retains its existing preparation-only contract. Resume and suspend broadcast because concurrent join callers can wait on the same condition.

These controls never pause an audio graph or mutate the render cursor. A playback host must pause its consumer separately, request suspension off the callback, and observe acknowledgment without blocking the main thread. If a consumer continues rendering, it can use already prepared audio and eventually reach the existing missing-successor stall. While suspended, the worker does not poll for render EOF/fault; resume or explicit stop wakes it to observe those states. Engine ownership, audio-session activation/deactivation, interruption policy, and the Play/Pause interface remain separate work.

Validation covers real cancellation during successor analysis, acknowledged and rapid resume, genuine-error preservation, idempotent controls, terminal shutdown, and exact continuation against the existing independent song sum. The real offline Apple graph also pauses and resumes twice while retaining sample-for-sample output at 32 kHz; the iOS integration test resumes the same source from its previous canonical position. These checks establish neither device pause latency nor background energy behavior.

Local validation on the pinned Xcode 26.6 toolchain passes all 100 audio tests in 32 suites in both Debug and Release. The 18 worker, suspension, cancellation, concurrent-handoff, and source-graph tests pass under ThreadSanitizer with Release optimization and sequential test scheduling; their internal worker/render/control threads remain concurrent. Nine iOS integration tests, one UI launch test, the unsigned Release iPhone build, staged formatting/lint, repository checks, and 13 extraction-guard tests pass.

All 193 deterministic Release exports (161 PCM files and 32 scalar JSON files) are byte-identical to PR #42. Native DSP, planning, the source callback, bank, fixtures, and reference tools are unchanged. The existing 14 reference comparisons were not rerun locally; hosted audio regression, size, and CodeQL checks remain required merge gates.
