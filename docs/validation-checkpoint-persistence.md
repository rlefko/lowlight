# Planning checkpoint persistence

`SessionPlanning.writeCheckpoint(to:)` saves the existing versioned musical-intent checkpoint to a file. `SessionPlanning.readCheckpoint(from:)` opens and validates that file, returning a restored planning owner or `nil` when the file is missing. The caller chooses a file URL in an existing directory and serializes all access to the owner and file off the audio callback. These synchronous operations also belong off the main thread.

Writing uses Foundation's [atomic replacement](https://developer.apple.com/documentation/foundation/nsdata/writingoptions/atomic): a completed temporary file replaces the destination. A failed save preserves the previous checkpoint. This does not promise power-loss durability. The existing sorted version-1 bytes, planning algorithm, control semantics, and history limits are unchanged; there is no new storage envelope or format migration.

Loading reads to EOF or one byte beyond `SessionTimeline.maximumCheckpointByteCount` (131,072 bytes). It handles short reads and rejects oversized input before decoding, without relying on file-size metadata. The existing restore path validates versions, plans, transitions, and the saved position. Invalid data, unsupported versions, and I/O failures propagate; reading never repairs, deletes, or overwrites a file. Both file operations run inside the existing preparation numeric scope, restoring the caller's floating-point environment on success and failure.

This API persists a planning cursor. `PreparedSession` plans ahead of audible playback, so its future checkpoint capture must coordinate the sounding position and pending work explicitly. A saved planner does not restore active voices, overlapping racks, room or limiter state. Playback integration, app lifecycle policy, and graceful user-initiated resume remain separate work; loading a file does not play audio.

The focused tests exercise real files: pristine and midstream continuation through 60→100→60 tempo changes, exact existing checkpoint bytes and frozen clock probes, replacement while a hard link retains the old file, exact-limit and oversized reads, corrupted and incompatible files, caller numeric modes, and failed replacement without losing the last good checkpoint. An iOS integration test covers file creation, restoration, and future planning inside the app container.

Local validation on the pinned Xcode 26.6 toolchain passed all 91 audio tests in 29 suites in both Debug and Release, all 25 planning tests in four suites in both configurations, eight iOS integration tests in two suites, one UI launch test, and the unsigned Release iPhone build. All 193 exported comparison files are byte-identical to the accepted PR #39 baseline, and all 14 existing audio reference gates pass. Formatting, lint, repository checks, and all 13 CodeQL extraction-guard tests also pass. The guard assertions now escape literal filenames, including the new Swift filename's `+`; the production extraction check is unchanged. Hosted CI remains a separate required merge gate.
