# Session audio engine ownership

`SessionAudioEngine(worker:)` adopts exclusive control of a ready preparation worker and privately owns its audio source and Apple engine. Construction connects the graph, requests preparation suspension, and stays silent. All access and final release must be serialized on a non-main control context, outside the audio callback. Stop and deinitialization can block while joining preparation; the future app coordinator must dispatch these operations appropriately.

The source retains its canonical 32 kHz stereo render block. Its planar stereo connection uses the current output rate, or the explicit manual-rendering rate in tests. Invalid output rates and unavailable output formats fail before attachment. Initialization failure stops and joins the adopted worker. No engine or source node escapes through the public API.

`play()` explicitly resumes preparation and starts the same graph; repeated calls while running do nothing. `pause()` first pauses the engine, preserving prepared resources and converter state, then requests cooperative worker suspension. Graph state becomes `paused` before preparation necessarily acknowledges `.suspended`. Immediate resume is supported without waiting for acknowledgment. The owner does not reset the source, effects, musical cursor, or pending song.

An engine-start error is terminal: the owner stops output, requests and joins preparation shutdown, detaches the source, then releases both owners off the callback. It stores and rethrows the original error. Rendering may have advanced before that error; the retained canonical position is a final snapshot, not a rollback or audible playhead. Explicit `stop()` and deinitialization follow the same ordered cleanup, and repeated stop is harmless. A stopped owner cannot play again.

Preparation errors remain visible separately from engine-start errors. Pausing and resuming do not clear a latched failure. `retryPreparation()` forwards an explicit retry request and returns false while preparation is suspended or stopped. A host can resume and then request retry; it must still respond to failures and sustained missing-successor silence. This owner adds no timer or automatic retry loop.

`state` describes the graph, independently of source EOF/fault and preparation status. Canonical EOF does not prove device conversion has drained, so the owner does not stop the engine on that snapshot. The host retains responsibility for completion and fault handling. Source status, canonical position, frame count, and any preparation error remain readable after stop.

Apple documents that [pause retains prepared resources](https://developer.apple.com/documentation/avfaudio/avaudioengine/pause()) and [stop releases them](https://developer.apple.com/documentation/avfaudio/avaudioengine/stop()). Device-mode start may implicitly activate the system audio session; the host must configure and activate the intended playback policy first. This change does not provide audio-session policy, interruptions/routes, background playback, asynchronous startup, or a Play/Pause interface. Tests use hardware-disconnected offline graphs and make no physical-device latency, conversion-cost, or energy claim.

Six focused tests exercise exact audio through repeated pause/resume and irregular pulls, explicit EOF behavior, stop and final release from each live control state, initialization failure, engine-start failures before and after rendering, and genuine preparation failures across pause, retry, and stop. They reuse the existing independent song sum and resource limits. Separate 44.1/48 kHz checks cover finite output, device-frame duration, and drained silence through the same owner. The iOS integration test uses the same owner to resume its source from the previous canonical position.

Local validation on the pinned Xcode 26.6 toolchain passes all 106 audio tests in 33 suites in Debug and Release. The 24 engine, source, suspension, worker, cancellation, and concurrent-handoff tests pass under ThreadSanitizer with Release optimization and sequential test scheduling; their internal roles remain concurrent. After a test-only weak-reference warning cleanup, the affected start-failure test is rechecked in Debug, Release, and ThreadSanitizer. Nine iOS integration tests, one UI test, the unsigned Release iPhone build, formatting/lint, repository checks, and 13 extraction-guard tests pass.

Every preexisting audio/planning/native production source, bank asset, fixture, and reference tool is unchanged. The existing 14 reference comparisons were not rerun locally. The new engine source is included in the required Swift extraction set; actual hosted CodeQL coverage, audio regression, and size checks remain required merge gates.
